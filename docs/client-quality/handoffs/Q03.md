## Implementation

- `include/realm/combat.hpp`, `src/combat.cpp`: `Combat` builds a uniform grid of enemy candidates lazily, once per `update()`, from the entity
  list (`build_target_index`), and enemy-targeting projectiles query the cells their +/-0.5 tile box touches (`query_target_index`).
  - Rebuilt every update, so movement, add/remove, map resets and client prediction cannot leave it stale; there is no invalidation protocol.
    Positions do not change inside `update()`. Candidates are re-resolved by entity id and every one goes through the *same* live `consider`
    predicate as before (targetable condition, hit history, 0.5 box, distance), so eligibility and multi-hit history are untouched. No pointer is
    stored across dense-container mutation (projectile removal swap-erases entities mid-update).
  - Ties: the original strict `<` over the dense list picked the earliest entity. `consider` now picks the lower dense index on an exact distance tie
    (`&e<target`), which reproduces that whatever order candidates are visited and after mid-update swap-removal reorders the list.
  - Grid: bounding box of enemy positions, power-of-two cell size from 1 tile, cell count capped at max(1024, 4*enemies) so map size or a stray far
    enemy cannot inflate it; counting-sort layout; non-finite positions are never selectable in a scan either and are skipped; query box widened by 1e-6 so
    the inclusive floating `abs(dx)<=.5` test can never fall outside the visited cells; capacity shrinks after a crowd leaves.
  - `TargetSearch::scan` keeps the original full scan as the differential oracle; `REALM_TARGET_SEARCH=scan` selects it at construction for paired
    same-binary runs. `TargetStats` (queries, examined, builds, indexed) is exposed on `Combat`/`Session` and written to stress summaries
    (`target_queries`, `target_examined`, `target_builds`, `target_indexed`).
  - Zones: `combat.target_query` (now includes the one-per-update `combat.target_index` build inside it).
- `tests/combat_target_tests.cpp` + CMake `projectile_target_search`: hand-built exact ties (including after a swap-removal), random lattice/dense/
  boundary/outlier(NaN, inf, 1e6, outside map)/multi-hit scenarios with churn (move, condition, remove, add), no-enemy and map-reset cases; grid and
  scan run in lockstep on identical worlds and every update's packet bytes, surviving projectiles and hit histories, entity order and cues are digested and
  compared (56 checks). `--profile` prints the candidate-count table below. Mutation checks: removing the tie rule and narrowing the box to 0.25 both fail.
- Semantics not changed: hit rules, damage, protocol, collision against terrain/cover, expiry. No swept collision. Player-targeting (hostile) shots
  still consider only the local player.

## Differences, failures and limitations

- A box that really contains N enemies still costs N candidates per query (pathological row): the grid is 2.5x faster there only through cheaper skipping,
  not asymptotically. Q02 has no fixture that crowds one cell with live shots (S-cluster hits are 2 or 0); that case is covered by the profile table.
- S3 projectile fixtures contain no enemies; they measure the entity-scan overhead that dominated Q02's ranking, not enemy-crowd hit density.
- Short cold-frame discovery windows, not sustained capacity; the combined S3 client is still far from 144 Hz (`scene.build`, appearance, text), so S3/144 Hz
  is **unqualified**. No 30-minute soak (Q19). Mock/offline evidence, not live server.
- Rebuilding per update costs O(enemies) (0.03-0.09 ms at 3,000); a persistent index was rejected because positions are written from several places
  (`World::update`, movement/prediction, status interpolation, `entities()` mutable access) and staleness would silently change which shot hits.
- The old `examined` figure for scan counts only enemy-flagged entities; the original also took a catalog lookup for every one of the ~23,000 entities, which is
  why it cost 1.2 s.
- Pre-existing, unrelated warnings remain in `tests/dye_session_inputs.cpp`, `tools/skin_inputs.cpp`, `tests/player_menu_tests.cpp`.
- No required check was disabled, skipped or blank. Visual output is unchanged by construction (no render code touched); no new captures were taken.
